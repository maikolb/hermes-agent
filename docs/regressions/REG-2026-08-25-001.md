# REG-2026-08-25-001 — Honcho configured without a reachable backend

## Incident

Hermes profiles on Windows and the VPS were configured to use Honcho at
`http://localhost:8500`, but no service was listening there. The VPS runtime
also lacked the `honcho-ai` SDK. Persistent memory therefore failed open and
agents could repeat previously failed routes.

## Evidence

- Windows profile logs recorded connection refusals to localhost port 8500.
- VPS profile logs reported that the Honcho SDK was unavailable.
- `hermes honcho status --all` constructed named-profile keys with a dot even
  though runtime identity resolution uses the canonical underscore form.
- A fresh fleet probe initially had no reachable backend; after the repair,
  all six Windows and three VPS identities wrote and retrieved unique markers.

## Root cause

The client configuration had been copied without provisioning the backend and
Windows-to-VPS localhost tunnel it referenced. The status command independently
drifted from the runtime's canonical profile-host key function, obscuring the
misconfiguration for named profiles.

## Repair

- Deploy the official Honcho stack pinned to commit
  `cf07068d95cee717a84dfaacdf08863ce8ca26fc` on the existing KVM8.
- Run local `qwen2.5:7b` generation and `nomic-embed-text` embeddings through
  Ollama; do not depend on Honcho Cloud or paid model APIs.
- Bind Honcho to VPS localhost port 8500 and extend the existing persistent SSH
  tunnel so Windows localhost port 8500 reaches it.
- Install the SDK in both active runtimes and align stable workspace/peer maps.
- Use `profile_host_key()` in `honcho status --all` and cover it with a focused
  regression test.

## Prevention artifact

`tests/honcho_plugin/test_cli.py::TestCmdStatus::test_status_all_uses_canonical_profile_host_keys`
fails if status resolution diverges from runtime host keys again. Target
acceptance additionally requires health checks plus write/retrieve probes from
both Windows and the VPS.
