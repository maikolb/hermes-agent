# REG-2026-08-24-001 — Kanban concludes before Git delivery is proven

## Status

- Root cause confirmed; correction validated locally on the consolidated
  candidate; PR/CI and target validation pending.

## Reproducible scenario

1. Project OS creates a task with a canonical branch/worktree and starts a
   worker.
2. The worker marks the task complete after producing changes.
3. `complete_task()` persists `done` before proving commit, push, PR, checks,
   merge or ancestry in the configured base branch.
4. Cleanup runs best-effort after completion and swallows failure.
5. Dirty/unpushed worktrees remain, but the task has no durable owner/retry
   state. Manually named worktrees are outside the canonical task cleanup
   namespace altogether and accumulate indefinitely.

## Root cause with code evidence

- `tools/kanban_tools.py::_handle_complete` delegates directly to
  `hermes_cli/kanban_db.py::complete_task`.
- `complete_task` commits the terminal DB state before `_cleanup_workspace`.
- `_cleanup_workspace` is non-authoritative and catches cleanup errors.
- `_cleanup_worktree_workspace` considers a commit safe when reachable from
  any remote ref. It does not require a PR, successful checks, merge, correct
  base or proof that `main` contains the task commit.
- `check_respawn_guard` recognizes a PR URL comment but does not query or
  validate the PR.
- `self_repo_guard.py` correctly protects the installed checkout from unsafe
  Git mutations; it is not a delivery state machine.
- The currently accumulated named worktrees are not canonical `.worktrees/t_*`
  task paths, so Kanban teardown/GC has no ownership proof with which to prune
  them.

## Required correction

- Delivery becomes a server-enforced precondition for `done`, configured per
  project/board without hardcoded project names or remotes.
- Required proof: exact owned worktree/branch, clean tree, exact remote SHA,
  authoritative PR for configured head/base, successful checks, merged PR and
  `git merge-base --is-ancestor <task-head> <base-remote>/<base-branch>`.
- Persist a sealed `delivery_verified` receipt while the task is still
  non-terminal. Revalidate receipt integrity, ownership, cleanliness and exact
  task-head ancestry before marking `done` or emitting the completed lifecycle
  hook.
- Worktree reclaim is a separate durable post-terminal obligation:
  `cleanup_pending -> complete`, retried by the existing dispatcher only after
  the owning worker PID exits. This ordering is required because the worker
  calls `kanban_complete` while its cwd is still the worktree; synchronous
  prune-before-return would either remove a live cwd or deadlock waiting for the
  caller to exit. Cleanup failure must remain owned and retryable, never be
  swallowed as best-effort.
- Any failure stays visible and retryable as
  `completion_blocked_delivery`. Never force-remove dirty, manual,
  non-canonical or foreign worktrees.
- The Hermes self-repository must explicitly use the personal fork as head
  remote while upstream remains read-only. External projects provide their own
  head/base policy; `origin` is not assumed globally.

## Prevention gate

Deterministic coverage includes:

- uncommitted, unpushed and wrong-remote heads;
- absent/open PR, pending/failing checks and wrong base;
- squash/rebase result without task-head ancestry;
- successful merge-preserving PR and verified base ancestry;
- timeout, no-change task, TOCTOU dirtiness and crash after receipt/prune;
- manual/foreign worktree never removed;
- no completed lifecycle hook before a verified receipt.

Canonical broad focused command:

`.venv\Scripts\python.exe -m pytest -q tests/hermes_cli/test_git_delivery.py tests/hermes_cli/test_kanban_worktree_teardown.py tests/tools/test_kanban_tools.py tests/hermes_cli/test_kanban_lifecycle_hooks.py tests/tools/test_self_repo_guard.py tests/hermes_cli/test_worktree_gc.py`
