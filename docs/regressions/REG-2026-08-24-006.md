# REG-2026-08-24-006 — Delivery replay can reset proof or acknowledge the wrong turn

## Status

- Open: root cause confirmed and correction in progress.
- No exact-once claim is authorized. The hard-process delivery gate, stale
  fence tests and ambiguous-acceptance tests remain pending.

## Reproducible scenario and observed evidence

### Delivered obligation becomes pending again

1. Record a durable delivery obligation under a stable obligation ID.
2. Transition it to `delivered`.
3. Record the same stable obligation again during recovery.
4. The audited pre-correction `INSERT OR REPLACE` deletes/recreates the row and
   resets the terminal proof to a retryable state. The sweeper can then claim a
   response that was already delivered.

### Late acknowledgement terminalizes a newer turn

1. Create an obligation for turn A, then let the same session advance to a new
   deliverable for turn B.
2. Apply the delayed terminal update for turn A.
3. The pre-correction checkpoint update is keyed by session/status without an
   immutable turn/revision/content fence, so the old acknowledgement can mark
   the current checkpoint for turn B as delivered.

### Remote acceptance is ambiguous

1. Let the platform accept a send.
2. Terminate the process before the local delivered acknowledgement is
   persisted.
3. Recovery sees an attempting/failed local row and automatically retries,
   although the remote side may already have accepted the first send.

## Root cause

- The ledger treated an obligation ID as a replaceable row rather than an
  immutable identity with monotonic state transitions.
- Ledger rows were not bound to the checkpoint's exact `turn_id`, immutable
  deliverable revision and content hash.
- Checkpoint delivery writes were blind session-level mutations, so stale
  obligations could terminalize newer checkpoints.
- Local non-acknowledgement and proven remote failure shared a retry path.
  There is no general proof of exactly-once delivery after remote acceptance
  but before local acknowledgement.

## Required correction

- Insert each obligation once. A repeat must return
  `already_delivered`/`existing_in_flight`; an immutable identity collision
  must fail closed and must never replace the prior proof.
- Store and validate the checkpoint fence
  `(turn_id, deliverable_revision, content_sha256)` on every durable
  obligation. Conditional transitions may only move the matching row forward.
- Before claim/send/terminal update, reconcile the row with the current
  checkpoint. A stale row becomes superseded and cannot mutate the new turn.
- Treat acceptance-before-ack as `delivery_ambiguous`: do not automatically
  resend. Only authoritative platform reconciliation or explicit human action
  may resolve it.
