# REG-2026-08-24-011 — Honcho cache can retain the previous configured backend

## Status

- Root cause confirmed; corrected and reproduced locally; real SDK/service and
  target validation pending.

## Reproducible scenario

1. A long-lived gateway builds a Honcho client while `config.yaml` points
   `honcho.base_url` at endpoint A.
2. The same bound `HonchoClientConfig` remains alive while the configuration is
   changed to endpoint B.
3. A second acquisition returns the cached client for endpoint A.

The pre-correction cache key was calculated before the effective URL inherited
from `config.yaml` was resolved inside the client factory.

## Root cause with evidence

The consolidated resolution keyed explicit clients with `config.base_url`, but
that field can be empty when the effective URL comes from `config.yaml`.
`get_honcho_client()` returned a cache hit before executing the factory code
that resolved the file-backed URL.  The effective transport destination was
therefore absent from client identity.

## Correction

Resolve and normalize the effective URL and timeout before cache lookup, include
those sealed settings in the cache identity, and feed the same values to the
factory.  The existing per-identity cache and concurrency behavior remain in
place.

## Prevention gate

`TestGetHonchoClient::test_config_yaml_base_url_change_rebuilds_long_lived_client`
keeps one config object alive, changes only the file-backed URL, and proves a
new SDK client is built for the new normalized endpoint.  It passes locally;
the focused Honcho matrix reports 59 passed and 16 SDK-conditional skips.
