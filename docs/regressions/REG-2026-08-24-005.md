# REG-2026-08-24-005 — Production tool effects are not durably fenced against replay

## Status

- Open: root cause confirmed and correction in progress.
- The current focused unit subset is partial evidence only. Fresh-process
  crash/restart validation and repeated stress are not green yet.

## Reproducible scenario and observed evidence

1. Start a turn in a fresh Hermes home/session.
2. Execute a tool through the production executor whose real effect writes a
   marker, then terminate the child with `os._exit(88)` before a normal tool
   result can return.
3. Start a new process and load the same turn checkpoint.
4. The marker proves that the effect happened, but the audited pre-correction
   checkpoint remains in `planning` with no pending or unknown tool call.
   Nothing durable prevents the executor from applying the same effect again.
5. In the isolated checkpoint API, seed an unknown outcome and call the replay
   guard twice for the same canonical call. The first call blocks, while the
   second is allowed because the decision was consumed by process-local state
   rather than resolved by durable evidence.

The compaction crash harness supplied a positive control: process loss after a
real archive/compact operation and before acknowledgement restored the
compacted transcript. The failure is therefore specific to the production tool
effect boundary, not proof that the checkpoint store cannot survive process
loss at all.

## Root cause

- Tool-attempt/result checkpoint APIs and their tests existed, but the
  production effect boundary in `agent/tool_executor.py` did not invoke them.
- Consequently, a hard exit after an external effect could not leave a durable
  `pending`/`unknown` record for recovery.
- The pre-correction replay guard used a process-local “blocked once” set.
  An unresolved external outcome is durable state, so a volatile one-shot
  block is not an authorization to retry.

## Required correction

- After policy/middleware has produced the exact final arguments, persist the
  canonical call attempt before invoking its handler. Failure to persist must
  fail closed before the effect.
- Persist the corresponding result only after its canonical tool-result row is
  durable. A crash between those boundaries remains unknown.
- Keep an unknown call blocked across calls and process restarts. Permit a
  retry only after a tool-specific, authoritative readback stores a durable
  `safe_to_retry` disposition; generic model text cannot unlock it.
- Cover sequential, concurrent-batch and delegated/segmented execution paths
  without weakening the exact-call fingerprint.

## Prevention artifact and validation gate

Implementation/test surfaces in progress:

- `agent/tool_executor.py`
- `agent/turn_checkpoint.py`
- `tests/agent/test_turn_checkpoint.py`
- a fresh-process failure-injection test that uses an isolated Hermes home,
  a real filesystem effect, a synchronization barrier and forced child exit
  with Windows `CREATE_NO_WINDOW` where applicable.

Focused command while the implementation is in progress:

`.venv\Scripts\python.exe -m pytest -q tests/agent/test_turn_checkpoint.py`

The regression is not green until the fresh-process crash/restart replay is
also run at least 20 consecutive times and proves: one effect, one durable
unknown outcome, zero automatic replay and no visible Windows process.
