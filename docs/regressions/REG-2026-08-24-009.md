# REG-2026-08-24-009 — compaction checkpoint sealed the pre-salvage transcript

## Status

- Root cause confirmed; corrected and reproduced locally; whole-candidate and
  target validation pending.

## Reproducible scenario

1. A durable in-place compaction produces a near-break-even candidate.
2. The commit-site anti-growth guard mechanically salvages it into a smaller
   transcript.
3. The turn checkpoint has already sealed the hash of the pre-salvage
   transcript.
4. SQLite persists the salvaged transcript, but `commit_compaction()` compares
   it to the obsolete prepared hash and fails closed with
   `CheckpointConflictError`; the compensating rollback restores the original.

Deterministic reproduction:

```text
.venv\Scripts\python.exe -m pytest -q tests/run_agent/test_in_place_compaction.py::TestInPlaceAntiGrowthGuard::test_in_place_salvages_near_break_even_growth
```

Pre-correction result: one failure, with the live transcript differing from the
prepared `after` hash. The positive salvage log showed the transcript changed
between prepare and commit.

## Root cause with evidence

The local durable-checkpoint integration called
`TurnCheckpointStore.prepare_compaction(..., compressed)` before the upstream
commit-site anti-growth guard. `salvage_grown_transcript()` can subsequently
replace `compressed`, but the checkpoint was not prepared again. The database
and checkpoint therefore described different proposed transcripts even though
both mechanisms behaved correctly in isolation.

## Correction

Prepare phase 2 only after the anti-growth decision and any salvage have
finished, immediately before the in-place or rotation mutation. A refused
would-grow attempt now returns without sealing a transcript that will never be
committed.

## Prevention gate

The exact reproduction and the adjacent explicit-media regression file are
3/3 green after the correction. The full compaction/checkpoint/restart matrix,
process-loss replay and target canary remain required before release.
