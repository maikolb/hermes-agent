# REG-2026-08-22-002 — Jira intake stalls after successful curation

## Status

- Reaberta — reparo de registro/anexos validado localmente; retry autônomo no alvo pendente.

## Scenario

- A real sandbox WhatsApp batch produced ten durable source events and two sanitized Jira projections.
- The `Jira intake sandbox — Hermes` no-agent job remained running or failed while the outbox stayed at two pending records.
- Reproduction command after the focused fix: `scripts/run_tests.sh tests/tools/test_mcp_oauth.py -k cross_task`.

## Root cause

- MCP Python SDK 1.28.1 creates `OAuthContext.lock` as `anyio.Lock` and holds it across an async-generator yield in `async_auth_flow`.
- `httpx` can resume or close that generator from another task. AnyIO then raises `RuntimeError: The current task is not holding this lock`, cancelling discovery before Jira tools register.
- The cached Atlassian token was unexpired, the remote endpoint answered, and a direct authenticated MCP initialize returned HTTP 200. Authentication state and network reachability were not the cause.

## Prevention artifact

- Hermes replaces only an AnyIO-backed OAuth context lock with `asyncio.Lock` immediately after provider construction. Hermes' MCP transport runs on a dedicated asyncio loop, so this preserves serialization without AnyIO's cross-task release restriction.
- The regression test acquires the lock in one task and releases it in another, matching the failing invariant.
- Target validation must consume the durable outbox by stable dedupe labels and prove no duplicate Jira issue exists.

## Reabertura — issue criada com evidência ausente tratada como sucesso

### Cenário e evidência

- O batch nativo `2027115e783343862dc2` criou autonomamente `HIS-6` às `04:28:06`.
- O Jira retornou HTTP 500 nas três tentativas de attachment; o read-back confirmou `attachments=[]`.
- Apesar da falha material, o turno terminou com uma string `INTAKE_OK` e o adapter removeu o spool. O request passado com `--delete-request` também é apagado em `finally`, inclusive em erro.

### Causa raiz confirmada

- O contrato de conclusão não é transacional: criação da issue e sincronização de evidências não produzem um resultado terminal obrigatório para o transporte.
- O transporte de attachment oculta o corpo limitado da resposta Jira, impedindo classificar a causa do HTTP 500.
- A causa protocolar específica do HTTP 500 permanece hipótese até ser reproduzida por teste de serialização ou validada no alvo; nenhuma correção de multipart será promovida por suposição.

### Artefato de prevenção

- Testes devem provar que falha de attachment preserva request/spool, que replay idempotente reconcilia a issue já criada e anexa a evidência sem duplicar, e que `INTAKE_OK` só existe após confirmação completa.

### Correção implementada

- Falha ou resultado parcial mantém o request e o receipt durável para retry; remoção ocorre somente após conclusão terminal confirmada.
- O retry preserva a identidade da ocorrência, reconcilia a issue já criada e impede duplicação de comentário ou anexo.
- O writer de anexos usa boundary multipart determinístico com no máximo `70` caracteres e preserva detalhe limitado da resposta para diagnóstico.

### Validação atual

- A suíte do `hermes-intake-hub` passou `67` testes.
- A versão `0.4.1` foi instalada no venv vivo do Hermes; os hashes comparados dos módulos no source e na instalação são iguais.
- O runtime oculto foi recarregado como PID `56812`, sem janela visível observada.
- O estado é `validated-local`. `HIS-6` permanece somente prova histórica de criação autônoma sem anexos; ainda falta um retry natural concluir os anexos e o ACK sem intervenção para atingir `validated-target`.
