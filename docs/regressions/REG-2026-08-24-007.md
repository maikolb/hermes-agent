# REG-2026-08-24-007 — Ordinary final response is not an exact replayable checkpoint

## Status

- Open: root cause confirmed and correction in progress.
- Existing transcript-persistence tests do not prove exact durable delivery
  replay after process loss.

## Reproducible scenario and observed evidence

1. Run an ordinary text turn to completion through the real finalization path.
2. Confirm that the user and assistant messages are present in the durable
   session database.
3. Inspect the turn checkpoint before platform delivery or after forced process
   loss at that boundary.
4. In the audited pre-correction path, the checkpoint remains in `planning`
   with no pending deliverable even though the assistant final is durable in
   session history.
5. Restart the turn. Because recovery has no sealed final payload, it re-enters
   the model loop instead of replaying the exact already-composed answer. The
   final can be lost, regenerated differently or duplicated.

This is stricter than “the assistant row exists”: the outgoing payload may be
changed by final-response fill, footer/plugin transforms and surrogate
sanitization. Recovery must bind and replay the exact post-transform payload,
not an earlier model string or a newly generated substitute.

## Root cause

- Ordinary finalization persisted conversation history but did not mark the
  final response as a checkpoint deliverable after all output transforms.
- The finalizer did not bind the deliverable to an immutable turn/revision/hash
  fence for the delivery ledger.
- The conversation loop lacked a recovery branch that recognizes a pending
  exact final and skips model execution.

## Required correction

- In `agent/turn_finalizer.py`, after all final transforms and sanitization,
  reconcile the durable assistant tail to the exact outgoing response, flush
  it, then mark an `ordinary_final` deliverable with turn ID, immutable
  revision and content hash. Any failure must block the original send.
- Pass that fence through the gateway to the delivery ledger.
- On restart, when the checkpoint contains a complete pending deliverable,
  return that exact payload through the normal finalizer/delivery path without
  calling the model again.
- Preserve the separate ledger rule from REG-2026-08-24-006: exact payload
  recovery cannot justify an automatic resend when remote acceptance itself is
  ambiguous.
