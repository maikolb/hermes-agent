# REG-2026-08-24-004 — Exact-call redirect races with a different concurrent call

## Status

- `validated-local`; candidate merge pending.

## Reproducible scenario

1. Seed the guardrail with repeated failures for one canonical `web_search`
   call.
2. Submit that blocked signature and a different `web_search` query in the
   same concurrent batch.
3. Depending on thread order, the different query either executes or is
   rejected as a tool-wide redirected route.

## Root cause

The local redirect change stored an exact-call threshold in
`_redirected_tools`, although tool-wide escalation already has its own
same-tool failure threshold. Concurrent `before_call()` decisions could observe
that mutation in either order.

## Correction and prevention

- Exact repeated failure and idempotent no-progress redirects are stored by
  canonical signature.
- Tool-wide structural/same-tool thresholds remain tool-wide.
- A different argument/source through the same tool remains available as the
  intended recovery route.

Validation:

- focused guardrail group: 23 passed;
- concurrent regression: 20 consecutive process-level pytest invocations
  passed without an order-dependent result.

Command: `.venv\Scripts\python.exe -m pytest -q tests/agent/test_tool_guardrails.py tests/agent/test_tool_guardrail_strategy_redirect.py tests/run_agent/test_tool_call_guardrail_runtime.py`.
